# Local Storage Formats

This file specifies exactly how data downloaded from each cloud service is stored on disk under `dataExports/`.
The download skills in `.claude/skills/` follow this spec, and the dashboard reads data based on it.

> Sections 1–3 apply to **every** service. Sections 4, 5 and 6 cover Notion, Linear and GitHub.
> A new service gets its own section using the same common envelope. Gmail is skipped, with the professor's approval.

---

## 1. Folder layout

```
dataExports/
├── notion/
│   ├── _manifest.json                         # index of every stored item + log of export runs
│   └── pages/
│       └── <slug>_<hash8>/                     # one folder per Notion page
│           ├── metadata.json                   # common envelope + Notion metadata
│           └── content.md                      # the page body as Markdown
├── linear/
│   ├── _manifest.json
│   └── issues/
│       └── <IDENTIFIER>_<slug>_<hash8>.json    # one file per issue, e.g. HW-12_fix-login-bug_5e40f22b.json
└── github/
    ├── _manifest.json
    ├── repos/
    │   └── <owner>-<repo>_<hash8>.json         # one file per repository, e.g. bluebird-labs-apollo-api_1c2d3e4f.json
    └── issues/
        └── <repo>-<number>_<slug>_<hash8>.json # one file per issue or pull request, e.g. apollo-api-7_add-stock-alerts_9a8b7c6d.json
```

Folder names are the service names in camelCase: `notion`, `linear`, `gmail`, `github`, …

### Naming rules

| Part | Rule | Example |
|---|---|---|
| `<slug>` | Title in lowercase. Every run of characters other than `a-z0-9` becomes `-`, then the result is trimmed to 40 characters. If it ends up empty, `untitled` is used. | `Sprint Planning #3` → `sprint-planning-3` |
| `<hash8>` | The first 8 hex characters of `sha1(<service id>)`. This keeps names unique even when two items share a title. | `4f1c09ab` |
| `<IDENTIFIER>` | Linear's human-readable issue key (team key + number), so files sort and read like the Linear UI. | `HW-12` |
| `<repo>-<number>` | GitHub: the repository name (lowercase, same rule as `<slug>`) and the issue or pull request number, so files group by repository. | `apollo-api-7` |

Because names come from the item itself, items are easy to tell apart, and the same item always lands at the same path.

## 2. Common envelope (all services)

Every stored JSON record (`metadata.json` for Notion, the item `.json` file for Linear and GitHub) has this top-level shape.
The dashboard only needs these common fields to list and search items from **any** service.

```json
{
  "schemaVersion": "1.0",
  "service": "linear",
  "id": "the service's own unique id",
  "title": "human-readable title",
  "date": "ISO-8601 date/time used to sort the item (see each service)",
  "url": "link that opens the item in the original service, or null",
  "searchText": "lower-cased plain text of everything searchable",
  "exportedAt": "2026-10-14T18:30:00Z",
  "source": { "mcpServer": "linear", "tools": ["list_issues", "get_issue"], "query": "all open issues in team HW" },
  "data": { "...": "service-specific fields, see sections 4-6" }
}
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `schemaVersion` | string | yes | Currently `"1.0"`. |
| `service` | string | yes | Must match the folder name. |
| `id` | string | yes | The service's stable id, never generated by us. |
| `title` | string | yes | `"(untitled)"` if the source has none. |
| `date` | string | yes | ISO-8601. A date-only value (`2026-10-24`) is allowed when the source has no time. |
| `url` | string \| null | yes | |
| `searchText` | string | yes | Built by `tools/save_export.py` from the title, all string values in `data`, and the Markdown content. |
| `exportedAt` | string | yes | UTC time of this export, set by the save script. |
| `source` | object | yes | Which MCP server and tools produced the record, plus the user's request (`query`). |
| `data` | object | yes | Service-specific data. Always includes `raw`, the unmodified object the MCP tool returned, so no metadata is ever lost. |

Encoding rules: UTF-8 (Hebrew and other non-ASCII text is stored as-is, not escaped), 2-space indentation, `null` for missing values (never invented), and ISO-8601 for all timestamps.

## 3. `_manifest.json` (one per service)

```json
{
  "service": "notion",
  "schemaVersion": "1.0",
  "items": {
    "<id>": {
      "path": "pages/sprint-planning-3_4f1c09ab",
      "title": "Sprint Planning #3",
      "date": "2026-10-12T09:15:00.000Z",
      "firstExportedAt": "2026-10-14T18:30:00Z",
      "lastExportedAt": "2026-10-15T10:02:11Z"
    }
  },
  "runs": [
    { "at": "2026-10-14T18:30:00Z", "query": "all pages mentioning Apollo", "count": 6, "ids": ["..."] }
  ]
}
```

- `items` maps the service id to where the item is stored. `path` is relative to the service folder and uses `/`.
- `runs` is an append-only log of export runs. It shows when each download happened and what was asked.
- **Re-downloads overwrite and never duplicate.** If an item already in the manifest is downloaded again, it is overwritten in place. If its path changed (for example, the issue or page was renamed), the old file or folder is deleted first.

## 4. Notion — `dataExports/notion/`

Source: the official Notion MCP server (`https://mcp.notion.com/mcp`), using the tools `notion-search` and `notion-fetch`.

One folder per page: `pages/<slug>_<hash8>/`.

### 4.1 `content.md`

The page body exactly as `notion-fetch` returns it (Notion-flavored Markdown). It does not include the metadata, so it reads like the original page.
Database pages that have no body get an empty file.

### 4.2 `metadata.json`

Common envelope with:

- `id`: the page UUID with dashes (`1a2b3c4d-....`)
- `title`: the page title
- `date`: `lastEditedTime`
- `url`: the `https://www.notion.so/...` page URL

`data` fields:

| Field | Type | Description |
|---|---|---|
| `objectType` | `"page"` \| `"database"` | |
| `parent` | object | `{ "type": "workspace" \| "page" \| "database", "id": ..., "title": ... }` |
| `icon` | string \| null | Emoji or icon URL |
| `createdTime` | string | ISO-8601 |
| `lastEditedTime` | string | ISO-8601 |
| `createdBy` | string \| null | Display name or id |
| `lastEditedBy` | string \| null | |
| `archived` | boolean | |
| `properties` | object | For database rows: property name → plain value (text, number, date, select name, list of multi-select names, list of people names, checkbox). Empty `{}` for regular pages. |
| `childPages` | array | `[{ "id": ..., "title": ... }]` sub-pages linked from this page (they are not downloaded automatically) |
| `contentFile` | string | Always `"content.md"` |
| `contentLength` | number | Character count of `content.md` |
| `raw` | object | Unmodified `notion-fetch` result, without the Markdown body (which is in `content.md`) |

## 5. Linear — `dataExports/linear/`

Source: the official Linear MCP server (`https://mcp.linear.app/mcp`). The download skill uses only its read tools: listing and getting issues, and listing comments. Tool names may carry a prefix such as `mcp__linear__`.

One JSON file per issue: `issues/<IDENTIFIER>_<slug>_<hash8>.json`.
The issue description (Markdown) and its comments are stored inside the same file, so one issue is one self-contained record.

Common envelope with:

- `id`: the issue UUID
- `title`: the issue title
- `date`: `updatedAt`
- `url`: the `https://linear.app/...` issue URL

`data` fields:

| Field | Type | Description |
|---|---|---|
| `identifier` | string | Human-readable key, e.g. `HW-12` |
| `description` | string \| null | Issue body as Markdown |
| `state` | string \| null | Workflow state name: `Backlog`, `Todo`, `In Progress`, `Done`, `Canceled`, … |
| `priority` | number \| null | `0` none, `1` urgent, `2` high, `3` medium, `4` low |
| `priorityLabel` | string \| null | e.g. `High` |
| `team` | object | `{ "id": ..., "key": "HW", "name": ... }` |
| `project` | object \| null | `{ "id": ..., "name": ... }` |
| `assignee` | object \| null | `{ "id": ..., "name": ..., "email": ... }` |
| `creator` | object \| null | Same shape as `assignee` |
| `labels` | array | Label names, e.g. `["bug", "frontend"]` |
| `dueDate` | string \| null | `YYYY-MM-DD` |
| `estimate` | number \| null | |
| `cycle` | object \| null | `{ "id": ..., "number": ..., "name": ... }` |
| `parentId` | string \| null | Parent issue id for sub-issues |
| `comments` | array | `[{ "id", "author", "body", "createdAt" }]`, oldest first |
| `createdAt` | string | ISO-8601 |
| `updatedAt` | string | ISO-8601 |
| `completedAt` | string \| null | ISO-8601 |
| `raw` | object | Unmodified issue object from the MCP tool |

## 6. GitHub — `dataExports/github/`

Source: the official GitHub MCP server (`https://api.githubcopilot.com/mcp/`), authenticated with a personal access token that is read from the `GITHUB_PAT` environment variable and never stored in the repo. The download skill uses only read tools, for example `get_me`, `search_repositories`, `get_file_contents`, `list_issues`, `issue_read`, `list_pull_requests` and `pull_request_read`. Tool names may carry a prefix such as `mcp__github__`.

Two kinds of items, each one JSON file:

- **Repositories:** `repos/<owner>-<repo>_<hash8>.json`
- **Issues and pull requests:** `issues/<repo>-<number>_<slug>_<hash8>.json`. Pull requests share the folder with issues, as they do in GitHub itself, and are told apart by `data.kind`.

The body (README or issue text) and the comments are stored inside the same file, so one item is one self-contained record.

Common envelope with:

- `id`: GitHub's global `node_id` (e.g. `R_kgDO…` for a repo, `I_kwDO…` for an issue). If the tool does not return it, the item's `html_url` is used instead.
- `title`: `owner/repo` for repositories; the issue or pull request title otherwise
- `date`: `updatedAt`
- `url`: the `https://github.com/...` page of the item

`data` fields for **repositories** (`kind: "repo"`):

| Field | Type | Description |
|---|---|---|
| `kind` | string | `"repo"` |
| `fullName` | string | `owner/repo` |
| `owner` | string | Account or organization login |
| `name` | string | Repository name |
| `description` | string \| null | |
| `visibility` | string \| null | `public` or `private` |
| `defaultBranch` | string \| null | |
| `language` | string \| null | Main language |
| `topics` | array | Topic names |
| `stars` | number \| null | |
| `forks` | number \| null | |
| `openIssues` | number \| null | |
| `license` | string \| null | License name |
| `homepage` | string \| null | |
| `readme` | string \| null | README file contents as Markdown |
| `createdAt` | string | ISO-8601 |
| `updatedAt` | string | ISO-8601 |
| `pushedAt` | string \| null | ISO-8601 time of the last push |
| `raw` | object | Unmodified repository object from the MCP tool |

`data` fields for **issues and pull requests** (`kind: "issue"` or `"pull_request"`):

| Field | Type | Description |
|---|---|---|
| `kind` | string | `"issue"` or `"pull_request"` |
| `repo` | string | `owner/repo` the item belongs to |
| `number` | number | Issue or pull request number |
| `body` | string \| null | Text as Markdown |
| `state` | string \| null | `open` or `closed` |
| `stateReason` | string \| null | e.g. `completed`, `not_planned` |
| `author` | string \| null | Login of the person who opened it |
| `assignees` | array | Logins |
| `labels` | array | Label names |
| `milestone` | string \| null | Milestone title |
| `merged` | boolean \| null | Pull requests only; `null` for issues |
| `draft` | boolean \| null | Pull requests only; `null` for issues |
| `comments` | array | `[{ "id", "author", "body", "createdAt" }]`, oldest first |
| `createdAt` | string | ISO-8601 |
| `updatedAt` | string | ISO-8601 |
| `closedAt` | string \| null | ISO-8601 |
| `raw` | object | Unmodified issue or pull request object from the MCP tool |

## 7. How data is written

The download skills never hand-write files into `dataExports/`. Each skill first gathers its envelopes into a JSON batch file under `.tmp/` (git-ignored), then runs:

```bash
python tools/save_export.py --input .tmp/<service>-batch.json --query "<what the user asked for>"
```

The script applies every rule above: naming, layout, `searchText`, `exportedAt`, the manifest, and stale-path cleanup.
Because of this, two runs at different times, in different conversations, always produce the same format.
